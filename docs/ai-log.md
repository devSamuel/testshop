# How I used AI on this project

The requirements close with *"we want you to ask the right questions and guide AI to make use of your experience and foreseeing skills."* This log records how I did that: the questions I asked, the guardrails I set, and the places where the AI's first answer was wrong or naive and how it was caught.

**Tooling:** Claude Code (Claude Opus 5.5) in VS Code, partly from the Claude mobile app via Remote Control.

**Rule I followed:** nothing was accepted because it looked right. Every behaviour is pinned by a test against real Postgres, and the risky ones by property-based tests or the chaos script.

## 1. Planning before code

| I asked | What changed because of it |
|---|---|
| Which approach to take, and what to implement | Instead of a feature list, I listed the failure modes the requirements hint at: dirty CSV (`stock (string/int)`), overselling, float money, double-click payments, deleting products with orders, `LIKE` search. Each became a requirement with a test. |
| "Shouldn't an enterprise app use the saga pattern with a message broker like Kafka?" | We compared a full broker-based saga with a modular monolith. The deciding argument: a saga *replaces* an ACID transaction when you can't have one, and here everything lives in one Postgres. I kept the saga where it is real (the external payment provider), added a transactional outbox so a broker can be plugged in without touching domain code, and documented the path in [`evolution.md`](evolution.md). |
| "If checkout is synchronous, won't concurrent buyers bottleneck the database?" | This produced three concrete additions: the row lock is held only for the reservation transaction (payment is outside it); a **202 Accepted fallback** when the provider is slow, settled by the reconciler; and a **hot-product benchmark** that measures throughput on a single contended row. |
| Which extras the requirements imply, beyond the feature list | I mapped every extra to a phrase in the requirements: the "proposed" CSV structure became a CSV contract critique; "date you downloaded" became a fuzz-tested importer; "foreseeing" became `make chaos`; "enterprise-grade" became an append-only inventory ledger. |
| "How does the upload actually travel: which headers, where is it parsed, are we loading it into memory?" | The answers were verified against the library source, not recalled from memory. That surfaced two facts: the endpoint runs only after the upload finishes, and the file is on disk twice. I kept the design and documented the trade-off in [`upload-path.md`](upload-path.md). |
| *(I provided the official example file)* "Decisions and rules should be taken from the file; if you detect more, document them and tell me." | Every rule now traces to a row in the real data. Reading all 97 rows found traps the automatic profile alone hadn't flagged (XSS and SQL-injection names, a missing column, a `99999` placeholder, an identical duplicate), which produced five refinements. SQL-looking text is deliberately kept verbatim, because parameterized SQL is the real defence |
| "If we are limited by the GIL, shouldn't the workers be an isolated container that just polls?" | The 4 dispatcher "workers" were asyncio tasks on the API's own event loop: one thread, so at most one core, shared with checkout requests. A polling-only `worker` container became the default, scaled by container (`make up WORKERS=N`), not by tasks. When I saw the in-process path still in `main.py`, I pushed further: the worker is the future broker relay and belongs in its own container, so the in-process option was **removed** and the API serves endpoints only. A new `make drain-bench` measured **1,223 → 2,343 → 3,511 events/s** with 1, 2 and 4 containers, with one container pinned at ~100% of a core while Postgres sat at ~25–35%. |
| "By moving to isolated workers, did we miss the reconciler, notifications, alerts and so on?" | Checked against the live database instead of answering from memory. Nothing was lost: 807 closed orders with 807 notifications, 4,102 alerts, 0 orders left pending, and the 5 orders expired during the chaos run were settled by the reconciler in the worker. The check found a real gap: `make up WORKERS=N` also multiplied the reconciler, with N copies asking the payment provider about the same orders. It's now **single-active through `pg_try_advisory_lock`**, with a test for it, plus a test proving the worker process alone reconciles, notifies and alerts. |

## 2. Guardrails I set up front
- Money is `Decimal` / `NUMERIC(12,2)`; never round money silently. The frontend sums in integer cents.
- Stock is reserved with one conditional `UPDATE … WHERE stock >= :qty`, never check-then-update.
- Every `POST /orders` requires an `Idempotency-Key`. A replay returns the same order; reusing a key with a different cart is rejected.
- No database transaction is held open across the payment call.
- Every side effect goes through the outbox, and handlers must be idempotent.
- The importer must never guess. Ambiguous values are row errors, not "best effort".
- Tests use real Postgres. SQLite would hide exactly the bugs that matter here.
- There are no comments in the code, as requested; the reasoning lives in the README and the ADRs.

## 3. Where the AI was wrong, and how it was caught

| # | First version | How it was caught | Fix |
|---|---|---|---|
| 1 | The import service logged `extra={"created": …}`. `created` is a reserved `LogRecord` attribute, so at INFO level **every successful import would have raised after committing** and returned a 500. | The **Hypothesis state machine** hit it on its first run. A manual CLI import at WARNING level had hidden it. | Renamed the log keys, scanned every `extra=` for reserved names, and hardened the JSON formatter so extras can never overwrite core fields. |
| 2 | Rows with more values than the header produced a *warning*. An unquoted `12,99` would have imported **price 12, stock 99, weight 200 kg**. | Writing deliberately dirty test data. | Extra non-empty values now make the row an error with a "probably shifted by an unquoted comma" message. |
| 3 | The low-stock alert fired only when stock *crossed* the threshold downward, using the event's numbers. Products imported with low stock never alerted, and out-of-order delivery could produce wrong alerts. | Smoke-testing the UI flow after an import. | The handler now **converges on current state**: it re-reads stock and opens or resolves alerts. A partial unique index allows at most one open alert per product. A test delivers events in reverse order. |
| 4 | Typo search used one trigram threshold. "headphnes" matched, but "keybaord" (similarity 0.44) did not. Lowering the global threshold would have added noise to every query. | An integration test. | A strict search runs first; if it finds nothing, a **fuzzy fallback** runs and returns `fuzzy: true`, so the UI shows "approximate matches". |
| 5 | The first plan had the sweeper expire any `pending_payment` order past its TTL. If the process crashed *after* a successful charge, the customer would be charged while their stock was released. | Walking through the saga step by step while explaining it. | The reconciler asks the provider for the charge status before expiring. A charge that succeeds after expiry raises `RefundRequired`, and an invariant checks that no customer is charged for an unpaid order. |
| 6 | The payment invariant queried the fake provider's table directly from the orders module, coupling the domain to an adapter. | Code review against the module-boundary rules. | The check goes through the `PaymentProvider` port, so it works unchanged with a real provider. |
| 7 | Postgres 17 was the initial choice, but the image pull stalled on the build machine. | Environment check. | Switched to Postgres 16, which supports every feature used (generated columns, `pg_trgm`, `SKIP LOCKED`). The ADR records it. |
| 8 | A 100k-row import took **143 s**, while 50k took 13 s. The first two guesses, stale table statistics and the background dispatchers competing, were both **disproved by measurement**. | `make seed-large`, then instrumenting every SQL statement by type. The existing-SKU lookup grew from 70 ms to 490 ms per batch. In `psql` the same query took 0.5 ms. | Root cause: asyncpg prepared statements made Postgres switch to a *generic plan* chosen while the table was empty (a sequential scan) and reuse it as the table grew. The fix is `plan_cache_mode = force_custom_plan`, scoped to the import transaction. **143 s → 17 s.** |
| 9 | The import ran as one transaction per file. That's simple and atomic, but it held row locks on every updated product until commit, so checkouts of those products would hang for the whole import. | Asking "what happens to checkouts during a large import?" after measuring the import time. | Per-batch commits, safe because re-running a file is idempotent. A `running` import record is written first, so every ledger entry has an audit parent. A failure-injection test verifies that a re-run converges. |
| 10 | The outbox dispatcher used one transaction per event: correct, but about 700 events/s, so a 100k import left alerts minutes behind. | Watching `/api/admin/outbox` drain after the bulk import. | Batched claims with a savepoint per event, plus 4 parallel workers. Parallel workers introduced a stale-alert race, fixed with a per-product advisory lock and aggregate-ordered batches (no deadlocks). A test runs 4 dispatchers concurrently and checks that alerts converge. |
| 11 | The weight parser rounded *before* checking magnitude, so a 26-digit weight crashed with `decimal.InvalidOperation`. | **Hypothesis**, on a later run of the "any input yields a value or a structured error" property. | Check magnitude before rounding, with explicit regression cases. |
| 12 | An admin stock edit could silently overwrite units sold since the form was opened. Sales intentionally don't bump `version`, to avoid false edit conflicts. A delete without `version` skipped optimistic locking entirely. | I built the frontend with a sub-agent working from an API contract I wrote, and asked it to report backend gaps instead of working around them. | Stock edits carry an `expected_stock` precondition (a stale value returns `409`, and the UI offers to reload). `DELETE` now requires `version`. |
| 13 | **The import was not streamed.** The upload reached the endpoint as a stream, but `file.read()` loaded it whole, and the parser kept every row: 252 MB peak for a 12 MB file. The size limit only ran *after* the whole upload had been spooled to disk, so a multi-GB upload could fill the disk. | **I asked** "aren't we streaming from the front end to the endpoint?" The AI's honest answer was "only half way", backed by a hop-by-hop table and a memory measurement. | End-to-end streaming: early `413`, stream to disk with a checksum, batch-wise parsing, an `import_issues` table with a 1,000-issue preview and a streamed CSV report, apply by run id. 100k rows: **252 → 98 MB**; 1M rows run in 189–240 MB. Two surprises along the way: FastAPI turns any non-HTTP exception raised while reading the body into a `400`, so the limit raises `HTTPException(413)`; and the first memory test asserted something false ("constant memory"), which was rewritten to the true claim ("independent of file size; grows with distinct SKUs"). |
| 14 | The outbox dispatchers ran as 4 asyncio tasks **inside the API process by default**. The ADR said "the ceiling is Python, so it scales with replicas", without saying that the tasks share one core with HTTP requests, or that more tasks can't add CPU. | **I asked** "if we are limited by the GIL, shouldn't it be an isolated container that just polls?" | The polling-only `worker` container became the default, scaled with `make up WORKERS=N`, and the in-process option was later removed from `main.py`. A new `make drain-bench` measured **1,223 → 2,343 → 3,511 events/s** with 1, 2 and 4 containers; one container ran at ~100% of a core while Postgres sat at ~25–35%. The ADR now says it precisely: one event loop = one core, and the GIL is why threads don't help. |

## 4. How the work was split
- **Backend, architecture, tests and docs:** built in the main session, step by step against the plan. Each step was committed only after `ruff`, `mypy --strict`, the import-linter contracts and the tests passed.
- **Frontend:** built by a **sub-agent**, working in parallel, from a written API contract that covered shapes, error semantics, the idempotency-key lifecycle and the polling rules. I then reviewed its riskiest code (money in integer cents, key rotation, the 202 polling loop), re-ran all of its gates, and fixed the backend gaps it reported (row 12).
- **Measure, then fix:** every performance change above started from a measurement. Two plausible hypotheses were *disproved* before the real cause was found.

## 5. How AI-written code was verified
- `ruff` (with security and async rules), `mypy --strict`, and `import-linter` architecture contracts run in CI.
- 185 backend tests on real Postgres, including one that imports the official example file end to end:
  - table-driven parser tests;
  - Hypothesis fuzzing of the importer with arbitrary bytes;
  - races on the last unit, concurrent double-submits, and opposite-order carts (deadlock check);
  - crash recovery at every saga step;
  - a **stateful model test** that interleaves imports, checkouts, crashes and reconciliation, checking the ledger and payment invariants after every step.
- `make chaos` SIGKILLs the running container mid-checkout while 50 clients retry with their idempotency keys, then verifies that nothing was oversold, duplicated, lost or left pending.
