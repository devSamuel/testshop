# Build journal: what was done, what went wrong, what we learned

This is the full story of how the project was built, in the order it happened. It covers every significant problem: what it was, how it was noticed, its root cause, the fix, and the evidence that the fix works. It ends with the lessons learned.

I built the project pair-programming with an AI assistant (Claude Code). I made the architectural decisions and steered the scope; the assistant implemented, tested and measured under explicit guardrails. Where a decision or a question came from me, the journal says so.

- [`../ai-log.md`](../ai-log.md): the short version, focused on guiding the AI.
- [`../adr/`](../adr): the decisions themselves.
- [`../chaos.md`](../chaos.md) and [`../benchmarks.md`](../benchmarks.md): the raw evidence.

## 2. Timeline

### Phase 0: planning (no code)
1. **What the requirements emphasize:** the closing note ("ask the right questions… foreseeing skills") says what matters most. We listed the failure modes the text hints at:
   - dirty CSV (`stock (string/int)`)
   - overselling
   - float money
   - double-click payments
   - deleting products that have orders
   - `LIKE` search
2. **I chose:** Python + React, PostgreSQL, and a "focused and polished" scope.
3. **I asked:** "Shouldn't an enterprise app use a saga with a broker like Kafka?" We wrote up both options:
   - **A:** future-ready monolith
   - **B:** A plus an opt-in Kafka profile

   The deciding argument was that a saga *replaces* an ACID transaction when you can't have one, and here everything lives in one database. **I chose A.** Kafka became a documented evolution path.
4. **I asked:** "Won't synchronous checkout bottleneck the database?" That produced three additions to the plan:
   - the 202 fallback for slow payments
   - the hot-product benchmark
   - the scaling ladder
5. **Which extras?** Every extra was mapped to a phrase in the requirements:
   - CSV contract critique
   - fuzz-tested importer
   - `make chaos`
   - inventory ledger
   - AI log
   - reviewer's guide

### Phase 1: scaffolding
- Python 3.13 with uv, plus ruff (with security and async rules), `mypy --strict`, and `import-linter` contracts that enforce the module layers.
- Core pieces: settings, async database, RFC 7807 errors, JSON logs with request ids.

### Phase 2: backend modules, in dependency order
`events` (outbox, inbox, registry, dispatcher) → `catalog` (products, search) → `inventory` (reservations, ledger, alerts) → `payments` (port plus a fake provider with its own table) → `orders` (saga, reconciler) → `importing` (parser and service) → `api` → Alembic migration.

The migration was autogenerated, then completed by hand with the `pg_trgm` extension and an **append-only trigger** on the ledger. `alembic check` confirmed that the models and the migration match.

### Phase 3: smoke testing with curl
Exercised every checkout path: approve, idempotent replay, key reuse, decline, out of stock, slow payment. Problems #4 and #13 surfaced here.

### Phase 4: the test suite

### Phase 9: streaming imports (raised by me)
1. **I asked:** "Aren't we importing using streaming from the front end to the endpoint?" The honest answer was *only half way*. A hop-by-hop check showed:
   - the browser streams the upload, and Starlette spools it to disk;
   - then `file.read()` loaded the whole file into memory, and the parser kept every row;
   - measured: **128 MB in the parser for a 12 MB file**, and 252 MB peak for the whole process;
   - worse, the 20 MB limit was checked only *after* the whole upload had been written to temp disk.
2. **My direction:**
   - stream as we parse, writing the file to disk as it arrives;
   - keep today's inline preview for small reports;
   - for thousands or millions of rows, offer a streamed download of the full report;
   - document the presigned-S3 upload path for production, and add further considerations.
3. **What was built:**
   - `413` middleware that works from the header and from counted bytes;
   - an `UploadStore` port (local disk today, S3 later) that streams to disk with a SHA-256;
   - an encoding and line-count pre-pass;
   - batch-wise parsing and committing;
   - an `import_issues` table, with migration `0002` backfilling existing reports;
   - a 1,000-issue preview plus a severity-filterable CSV streamed from a database cursor;
   - **apply by run id**, so a large file is uploaded once and the applied bytes are the reviewed bytes.

   The frontend sub-agent updated the Import page in parallel from a written contract.
4. **Measured after:**

   | | Before | After |
   |---|---|---|
   | 100k rows (12 MB), process peak | 252 MB | **98 MB** |
   | 1M rows (122 MB) | rejected; ~2.5 GB extrapolated | dry run 15 s / **240 MB**; apply 176 s / **189 MB** |
   | 600k-issue report | capped at 10k stored issues | 35 MB CSV streamed in **1.3 s**; app process ≤ 214 MB |
   | 230 MB upload | written to disk, then 413 | **413 in 3 ms, 0 bytes uploaded** |
5. **Follow-up: "how do the bytes actually travel?"** I asked which headers the browser sends, where Starlette parses chunk by chunk, and whether `store_upload` / `open("wb")` loads the file into memory. Reading the FastAPI, Starlette, python-multipart and uvicorn sources gave the answers and surfaced two facts:
   - our endpoint only starts after FastAPI has finished parsing the whole upload;
   - the file is on disk twice: Starlette's spool file, plus our durable copy for apply-by-run-id.

   Memory is bounded either way, at about 1 MB per copy step. **I chose to keep the design and document it** rather than write custom multipart handling for a fraction of a second per 100 MB. See [`../upload-path.md`](../upload-path.md).

### Phase 10: microservice readiness, made concrete (raised by me)
- **I asked** where the docs say the system is modular and ready to become microservices "because these are separate and can be run by themselves". The claim existed only as one-liners in five places, and "can be run by themselves" wasn't yet true.
- **What was added:**
  - `python -m app.worker`, which runs the outbox dispatchers and the reconciler as their own process, with a shared `start_background_workers()` so the API and worker modes can't drift;
  - a compose profile and `make up-split` (the default stayed a single container until phase 12);
  - `RUN_MIGRATIONS=false` on the worker;
  - a CI step that starts split mode.
- **Demonstrated:** with the worker stopped, the API took 3 orders while 9 events waited in the outbox. With the worker restarted, they all drained and 3 notifications went out, with the invariants passing.
- **Documented honestly:** the README and `architecture.md` section 6 give the ownership map, the couplings that still tie the modules together (one shared database, cross-module foreign keys, reservations inside the checkout transaction), how each would be resolved, and the extraction order.

### Phase 11: the official example file defines the rules (directed by me)
- **I provided the example file** and directed that **the rules be taken from it**, with any extra rule documented and reported.
- **Profiling:** every planted problem was already caught by the existing parser: `$29.99`, `free`, `-5`, empty or whitespace-only names, conflicting duplicates, `0.00`, an empty category and blank rows. Reading every row found more:
  - an XSS name (row 20);
  - a SQL-injection name (row 29);
  - a missing weight column (row 50);
  - a `99999` "unlimited" placeholder (row 52);
  - an identical duplicate (row 89);
  - quoted commas, escaped quotes and Unicode.
- **Rules added from those rows:**
  - identical duplicate → warning;
  - HTML markup rejected (also at the API);
  - missing-weight and placeholder-stock warnings;
  - a clearer `free` message.

  SQL-looking text is deliberately kept; a test proves it round-trips and the table survives.
- **Result:** 95 rows → 87 imported, 7 rejected, 6 warnings, pinned by `test_official_example_file_end_to_end`. The app now seeds from the official file; the reviewer's-guide examples and the screenshots were redone against it.

### Phase 12: background workers in their own container (raised by me)
- **I asked:** "if we are limited by the GIL, shouldn't it be an isolated container that just polls?"
- **The reasoning, made precise:**
  - the 4 "workers" are asyncio tasks on one event loop, so one thread and at most one core;
  - inside the API process, they shared that core with HTTP requests;
  - the GIL is why threads wouldn't fix that, and why the scaling unit is a process.
- **What changed:**
  - compose now starts a polling-only `worker` container, and `make up WORKERS=N` scales it;
  - **the in-process option was then removed from `main.py`** (also at my direction). The worker is the future outbox → broker relay and belongs in its own container. The API serves endpoints only, and `make dev-worker` runs the worker in development;
  - each worker's pool is capped at 8 connections;
  - CI checks that the worker starts and scales to 2.
- **"Did we miss anything?"** I asked whether the reconciler, notifications and alerts survived the move.
  - The live database said yes: every closed order had its notification, the alerts were raised, and nothing was left pending.
  - The check also exposed that scaling the worker multiplied the reconciler. It's now single-active through a Postgres advisory lock.
  - A new test proves the worker process alone reconciles, notifies and alerts.
- **Measured** with a new `make drain-bench` on a ~50,000-event backlog: **1,223 → 2,343 → 3,511 events/s** with 1, 2 and 4 containers.
  - One container ran at ~100% of a core while Postgres sat at ~25–35%, so the event loop was the limit, not the database.
  - With 4 containers, each still ran at ~100% of a core, and Postgres rose to ~1.6–2.1 cores.
- **Re-verified:**
  - `make bench` in the new mode: the hot product at 85% of contention-free throughput.
  - A first run showed the spread case at half speed, right after a 100k-row bulk load. A second run matched the old numbers, so the first is attributed to post-load database work, likely autovacuum (not profiled).

## 3. Design decisions I made

| Question | Decision | Why |
|---|---|---|
| Saga plus Kafka for an "enterprise" app? | **No broker now.** In-process saga, transactional outbox, documented evolution path | One database means ACID beats eventual consistency. The outbox makes a broker a later addition with no domain-code changes |
| Synchronous checkout? | **Sync fast path, `202` fallback** | Users need to know immediately whether their card worked. Slow providers must not hold connections or locks |
| Which extras to build? | Ledger, chaos test, CSV critique, AI log | Each one answers a specific phrase in the requirements |
| Kafka at all? | Designed in [`evolution.md`](../evolution.md), not built | Knowing when *not* to build is part of the signal |

## 4. Problems in our own code: found, explained, fixed

Each row follows the same pattern: how the problem was noticed, its root cause, the fix, and the proof that the fix works.

| # | Problem | How it was noticed | Root cause | Fix | Proof |
|---|---|---|---|---|---|
| 1 | **Every successful import would have returned a 500** at INFO log level, after committing | The Hypothesis state machine, on its first run | `extra={"created": …}` collides with the reserved `LogRecord.created` attribute; a manual CLI import at WARNING level hid it | Renamed the keys, scanned every `extra=` for reserved names, and stopped the formatter from overwriting core fields | Full suite runs at `--log-level=INFO` |
| 2 | **Transposed-letter typos** ("keybaord") found nothing | Integration test | Trigram similarity 0.44 was under the 0.45 threshold; lowering the threshold globally would add noise to every query | **Fuzzy fallback:** a strict query first, a looser retry only if it finds nothing, and the response says `fuzzy: true` so the UI can explain | `test_transposed_letters_fall_back_to_fuzzy_matching`; nonsense still returns 0 |
| 3 | An unquoted `12,99` **shifted every column**: price 12, stock 99, weight 200 kg | Writing deliberately dirty test data | Extra columns were only a warning | Extra non-empty values make the row an **error** ("probably shifted by an unquoted comma") | `test_shifted_columns_from_unquoted_comma_are_rejected` |
| 4 | **Low-stock alerts** didn't fire for products imported with low stock, and depended on event order | curl smoke test after an import | The handler reacted only to a downward *crossing*, using numbers carried in the event | The handler **converges on current state**: it re-reads stock, then opens or resolves alerts. A partial unique index allows one open alert per product | Test delivers events in reverse order and still gets the right alert |
| 5 | **100k-row import took 143 s** while 50k took 13 s: quadratic | `make seed-large`; see the investigation below | asyncpg **prepared statements** made Postgres switch to a *generic plan* chosen while the table was empty (a sequential scan), and reuse it as the table grew | `plan_cache_mode = force_custom_plan` for the import transaction only; load only needed columns; bulk-insert ledger and outbox rows | **17 s**; linear (100k re-import 18 s; identical re-run 10 s) |
| 6 | **Outbox drained at ~700 events/s**, so a 100k import left alerts minutes behind | Watching `/api/admin/outbox` after the bulk import | One transaction per event; about 5 round-trips each | Batched claims with a **savepoint per event**, plus **4 parallel workers** | **~1,400 events/s**; 100k events in ~80 s |
| 6b | Parallel workers could leave a **stale alert** | Reasoning about the change in #6 before shipping it | Two workers handling the same product's events could interleave read → resolve → insert | **Per-product advisory lock** in the handler, and batches sorted by aggregate so workers take locks in the same order (no deadlocks) | `test_parallel_dispatchers_converge_on_correct_alerts` (4 dispatchers at once) |
| 7 | The benchmark's `EXPLAIN` **didn't show what the text claimed** | Reading the benchmark output | `ORDER BY id LIMIT 20` let Postgres walk the primary key and filter rows | Explain the realistic shape (ranking needs every match), and generate the commentary from the actual plan | The plan now shows a `BitmapOr` over all three indexes, 25 ms |
| 8 | The hot-product benchmark had **no control group** | Asking "is 124 orders/s limited by the lock or by Python?" | One number can't separate the two | Added the same load spread across 200 different products | Hot row reaches **87%** of the contention-free throughput at first (**85%** in the latest run), so the lock isn't the bottleneck |
| 9 | **Imports held row locks for the whole file**, so checkouts of updated products would hang for ~20 s during a big import | Asking "what happens to checkouts during a large import?" after measuring #5 | A single file-wide transaction | **Commit per batch.** Safe because a re-run is idempotent and the dry run has already validated everything. A `running` audit record is written first, so ledger rows always have a parent | Failure-injection test: a crash after batch 1 reports "50 of 120 rows applied" and a re-run converges |
| 10 | **Admin stock edits could erase sales**, and a **delete without `version`** skipped optimistic locking | The frontend sub-agent was told to *report* backend gaps rather than work around them | Sales intentionally don't bump `version`, to avoid false edit conflicts, so the version check can't see them | `expected_stock` precondition (`409` if stock changed since the form loaded); `DELETE` now requires `version` | Two new API tests; the UI reuses its "changed by someone else, reload" dialog |
| 11 | A 26-digit weight **crashed the parser** with `decimal.InvalidOperation` | Hypothesis, on a later run of the "any input gives a value or a structured error" property | The magnitude check ran *after* rounding to 3 decimals, which overflowed the 28-digit decimal context | Check magnitude before rounding | Explicit regression cases |
| 12 | The payment invariant **queried the fake provider's table** from the orders module | Review against the module-boundary rules | Convenience SQL crossed an adapter boundary | Moved the check behind the `PaymentProvider` port | `import-linter` contracts stay green; works with a real provider |
| 13 | The first saga plan **expired any pending order past its TTL**, even if the charge had succeeded before a crash | Walking through the saga while explaining it to me | Expiry didn't consult the source of truth for money | The reconciler asks the provider first. A late success raises `RefundRequired` instead of keeping the money silently | Three crash-point tests plus the `no_charge_without_paid_order` invariant |

### 4b. Found during the streaming rewrite

| # | Problem | How it was noticed | Fix |
|---|---|---|---|
| 18 | The import wasn't streamed, and the size limit ran after the whole upload hit the disk | **My question**; then a hop-by-hop check and `tracemalloc` | End-to-end streaming (phase 9) |
| 19 | The early-`413` middleware returned **400** when the body had no `Content-Length` | A test that streams an oversized body | FastAPI turns any non-HTTP exception raised while reading the body into "error parsing the body". The limit now raises `HTTPException(413)`, which FastAPI re-raises unchanged |
| 20 | The first memory test claimed "memory doesn't grow with rows", and it **failed** | Running it: 5k rows → 0.7 MB, 50k → 6.3 MB | The claim was wrong, not the code: duplicate detection needs an index of seen SKUs. The tests now assert the true property, independent of row width and bounded per SKU. The README's tens-of-millions path moves that index into Postgres |
| 21 | "Last row wins" for duplicate SKUs can't stream: you can't know a row is the last one until the file ends | Designing the batch flow | Switched to "first row wins, later rows are errors". It's streamable, and it refuses to guess. Later refined by the official file: identical repeats are skipped with a warning. Recorded in ADR 0005 and the README |

A deliberate trade-off also came out of this. The streaming dry run is about 1.7× slower on small files (1.8 s vs 1.1 s for 100k rows): the pre-pass, the per-batch issue writes and the thread hops for parsing cost a little. That was accepted in exchange for bounded memory and an event loop that stays responsive to checkouts during big imports.

### The investigation behind #5 (measure, don't guess)
Four plausible explanations were tested in order; the first three were disproved by measurement:

| Hypothesis | Test | Result |
|---|---|---|
| GIN index maintenance is slow | Pure SQL insert of 20k rows with all indexes | 241 ms: **disproved** |
| The Docker image runs under emulation | Inspected image architectures | All native arm64: **disproved** |
| Stale table statistics cause a sequential scan | Analyzed a tiny table, then `EXPLAIN` in `psql` | Index scan, 0.5 ms: **disproved** |
| Background dispatchers compete with the import | Same import with the app running and stopped | ~5 s both ways: **disproved** |
| **Something in the app's query path** | Instrumented every SQL statement by type | SKU lookup grew from **70 ms to 490 ms per batch**, while `psql` showed 0.5 ms for the same query. The only difference is prepared statements, so the cause is **generic-plan caching** |

## 6. Process lessons
- **Approvals from the phone:** in plan mode, typing a reply into the approval prompt counts as *rejecting* it with feedback. Tapping "Approve" is what continues. This cost a few round-trips, and is now remembered for future sessions.
- **Delegating with a contract:** the frontend was built in parallel by a sub-agent. What made that work:
  - a precise contract covering shapes, error semantics, the idempotency-key lifecycle and polling rules;
  - an instruction to **report backend gaps rather than work around them**, which produced fix #10;
  - reviewing its riskiest code ourselves and re-running every gate, instead of trusting its summary.

## 7. What we learned

### Engineering
1. **Measure before fixing.** Problem #5 had four plausible explanations; measurement disproved them one after another. Guessing would have shipped the wrong fix.
2. **Example tests confirm what you thought of; property-based and model-based tests find what you didn't.** Two production-grade crashes (#1, #11) were found by Hypothesis, not by hand-written cases.
3. **Write adversarial test data.** Dirty input, written to test the importer, revealed a design flaw (#3) that clean data never would.
4. **Handlers should converge on current state, not replay event payloads.** That makes duplicates and out-of-order delivery harmless (#4), which is a prerequisite for adding a broker later.
5. **Prepared statements plus a table that grows inside one transaction is a performance trap.** A plan that's optimal for an empty table is cached and reused at 100k rows (#5).
6. **Long transactions are availability bugs.** Idempotency is what makes it safe to shrink them (#9).
7. **A benchmark without a control group and a realistic query proves nothing** (#7, #8).
8. **The source of truth for money is the payment provider.** Never release or expire an order without asking it first (#13).
9. **Design for the future, but don't build it yet.** The outbox and the ports cost little and make Kafka cheap later. Building Kafka now would have cost the consistency guarantees.
10. **An importer must refuse to guess.** Silent coercion (rounding money, `N/A` → 0, shifted columns) is worse than a clear row error.
11. **Ask "where does the data actually sit?" at every hop.** "We upload a file" hid a full in-memory copy and a size check that ran after the disk had already filled (#18). A memory test that fails can mean the *claim* was wrong (#20).

### Working with AI
1. **The value is in the questions.** My three questions (broker? bottleneck? which extras?) shaped the architecture more than any amount of generated code.
2. **Guardrails up front** (Decimal money, conditional `UPDATE`, idempotency keys, real Postgres in tests, no guessing) prevented a whole class of naive suggestions.
3. **Treat AI output like a junior colleague's pull request.** Every bug in section 4 came from a plausible first version that looked right. Tests, measurements and review caught them, not confidence.
4. **Make the AI prove claims with evidence:** invariants, chaos runs, benchmarks with controls. "It should work" is not evidence.

## 8. Known limitations and open items

| Item | Status |
|---|---|
| Official example file | ✅ `data/products.csv` (downloaded 2026-10-02); its rows define the import rules (phase 11) |
| Build with official base images | ✅ Verified in CI: the Docker job builds the official images (amd64) and passed on 2026-10-03. Local builds used the build-arg stand-ins (#14) |
| GitHub | ✅ Pushed on 2026-10-03; the first CI run passed |
| Authentication and authorization | Not built, by decision. The admin pages and the full orders list, customer emails included, are open to anyone. | Import rejection body | Returns the import report shape rather than problem+json (documented: the report *is* the useful payload) |
| Idempotency fingerprint | Uses the card's last 4 digits, never the full number, by design (PCI). A reused key with a different card that has the same last 4 replays instead of returning `422` |
| Throughput ceiling | One uvicorn worker per container. Scale with workers or replicas; the dispatcher and reconciler are already multi-replica safe |
| Very large imports | Processed inside the HTTP request: a 1M-row apply takes ~3 min. The production path (presigned S3, queue, worker with progress) is designed in [scaling.md](../scaling.md), not built |
| Duplicate index memory | ~100 bytes per distinct SKU (~110 MB at 1M). Moving it to an unlogged Postgres table is the next step for tens of millions of rows |
| Early 413 in browsers | When the server answers before the body finishes, some browsers report a connection reset instead of the 413. The UI's own 200 MB check catches oversized files before upload |
| Broad search queries | 60–200 ms on the synthetic catalog, which has only 200 name patterns; keyset pagination and a search engine are documented next steps |
